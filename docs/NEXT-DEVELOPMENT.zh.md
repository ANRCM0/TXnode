# TXnode 后续开发方案

日期：2026-10-20（Asia/Shanghai）

方案基线：`main@25e6da54bfaf4c6d7c0ed2e78ea2f6b60cf5fc90`

对照基线：原双内核版本 `a1ad2695e1143269168c36a274283de3342e91c7`

状态：本文保留实施目标和首次执行前固定的验收口径。S0-S4 的源码与测试已分批编写；
当前实现和候选验收状态见 `OUTSTANDING-WORK.zh.md`。本方案本身不是验收报告。

## 1. 目标和交付范围

将当前原生节点推进到可持续验证、可发布、可受控试运行的版本。优先收敛已经提供的协议和业务语义，再扩展低优先级能力。

本轮的四个交付目标：

1. 互通测试能够阻断真实回归，连接失败、缺少必需客户端和意外跳过均不能被视为通过。
2. 常用客户端组合和剩余 UDP 路径进入统一授权、路由、准入、限速与计量链路。
3. 取得原生内核的故障恢复、持续运行及新旧性能对照证据。
4. 打通开发镜像发布，并为后续 Core 采用和预发布保留可追溯的提交、镜像摘要与契约证据。

保留现有职责：Core 拥有身份、权益和结算；Provider 拥有凭据及授权交付；Node 执行数据面与使用量证据采集。继续使用唯一的 `txnode` 内核，不恢复 sing-box/Xray 服务端，也不增加另一套计量账本。

## 3. 各阶段共同遵守的调用链

```text
service / Kernel 配置与授权代际
  -> liveHandler / 协议认证 / Tracker 准入
  -> core.Server.ServeSession / MuxStreamSession
  -> 统一路由、目标拨号、设备与连接门禁、限速、relay
  -> NativeMeter Begin/Complete（实际客户端 I/O）
  -> 原代际 NativeCollector / 持久化日志 / 上报
  -> Core 结算及回执
```

- 协议层拥有线格式、加解密、分片/重组、重传和会话状态机；认证成功后的目标拨号与业务策略继续交给 core。
- 新 UDP/mux 子会话必须继承用户、真实来源、认证有效性和取消信号，登记到既有连接生命周期。父连接撤权和子会话关闭都要有计量尾部。
- 同一份业务字节只计量一次。协议头、ACK、重传、padding 不得因协议重试重复形成业务使用量；具体边界以现有计量契约和客户端实际 I/O 为准。
- 用户轮换、删除重加、服务器重载和计量换代都不得复活旧认证；旧 I/O token 的 Complete 仍归原 collector。
- 每个切片必须说明完整调用链及兼容入口。配置、renderer 或对外能力声明发生变化时，单独评审对应契约和版本。

## 4. 分阶段实施

### S0：先让验收结果可信

目标：区分真实通过、明确不支持、尚未完成和环境不足，建立后续开发可用的门禁。

实施内容：

1. 为互通用例建立固定客户端版本、预期结果、责任范围和缺口编号清单。保留已有版本及 SHA-256；引用协议源码时还要记录客户端实际使用的依赖 revision。
2. 在完整验收模式检查必需二进制、REALITY 密钥和证书夹具。缺少必需输入直接失败；仅在普通本地发现模式允许缺少客户端时跳过。
3. 将已声明支持的链路从“连接失败转 Skip”改为失败。完整矩阵输出 `go test -json` 与结构化汇总；新增或原因不匹配的 Skip 使门禁失败。
4. 对已知缺口使用显式清单记账，不能匹配任意连接错误。该用例的回归预算是基线数而不是永远写死的“允许 6 个 Skip”；修复后收紧清单。
5. 增加 PR 快速互通矩阵，覆盖 VLESS/VMess/Trojan/SS、一个 QUIC TCP/UDP 路径和一个 mux TCP 路径；完整矩阵保留在 dispatch/nightly/tag，并作为候选版本门禁。
6. 输出一份行为覆盖表，将挂起测试中的原业务断言映射到真实原生测试；优先补事件持久化、observer 和 packet 周期，保留原始计量与恢复断言。
7. 修复 SIGKILL 故障夹具的固定等待：以持久化后的阶段标记/进程握手协调崩溃时机，设置明确上限并输出诊断。环境不足单独报告，不能以扩大 Skip 或超时掩盖计量问题。

主要位置：`internal/kernel/txnode/interop_test.go`、`internal/service/*_test.go`、`internal/usageinterval/*_linux_test.go`、`scripts/`、`.github/workflows/ci-node.yml`、`docs/removed-tests/README.md`。

验收：已支持链路发生真实连接错误时 CI 必须失败；必需客户端缺失和意外 Skip 必须失败；原始周期、崩溃恢复和 packet 计量断言在真实内核入口执行。预期不支持项单独展示，不计入通过数。

### S1：收敛现有客户端兼容性

目标：先解决已经声称支持、但当前证据不完整的客户端组合。

| 工作项 | 实施方法 | 完成标准 |
| --- | --- | --- |
| Mihomo REALITY | 使用同一临时密钥对配置服务端和客户端，CI 自动提供公钥 | 固定 Mihomo 客户端真实请求通过，缺少公钥不再跳过 |
| sing-box Naive | 对齐证书链、SAN、SNI 与信任方式，保留证书校验 | 固定客户端 h2 CONNECT 实际通过；错误证书仍应失败 |
| Mihomo TUIC | 对照同版客户端连参考服务端和 txnode 的握手、ALPN、exporter 与认证流布局，先定位再修复 | 形成可复现差异及责任结论；修复目标是 TCP/UDP 均通过，不能只去掉 Skip |
| 上游明确不支持项 | 固定 Xray H2 和 sing-box Mieru 的版本事实；Mieru 功能继续由官方客户端验收 | 作为不可用组合列出，有替代验收，不要求无意义的零 Skip |

已有错误处理、认证有效性、设备限制和计量断言必须同时保留。新增客户端版本属于单独变更，不能靠升级客户端绕开同版回归。

### S2：补齐 UDP，拆成两个独立切片

#### S2-A：smux/yamux 地址头 mux UDP

先补常用 mux 组合，避免将它与已完成的 Mux.Cool/XUDP 混成一个能力。

- 从固定 sing-box 客户端对应的 `sing-mux` 源码和原生参考服务端确认 packet-stream 请求、首包应答、地址及报文边界，记录最小线格式夹具。
- 修正现有 `mux.Packets` 与客户端格式之间的适配；继续通过既有 mux child session 和统一 packet relay，不增加协议内目标直拨。
- 覆盖同一父连接的 TCP/UDP 混用、多目标、双向数据、报文长度、断流、撤权、限速和计量尾部；分别测试 smux 与 yamux。
- 检查多 Node 实例并存时的 mux 归属，确保不会使用另一实例的 Server、用户表或 meter。

验收：固定 sing-box 的 smux/yamux UDP 真实双向通过，且父认证失效后子流立即失效；路由阻断和计量结果与普通 UDP 一致。完成前仍按未验收能力展示。

#### S2-B：Mieru v2 UDP 承载

- 以官方 mieru `v3.38.1` 的包承载与 session 状态机为参考，先对齐 open/ACK、序号、窗口和重传推进条件。
- 将协议传输本身的确认与应用数据交付分开，处理丢包、乱序、重复、分片/重组、超时和关闭。
- 为 peer、待确认窗口、重组缓存、重传次数及存活时间设置上限；超限行为可观测并可测试。
- 认证成功后创建现有 `core.Session` / packet relay，沿用用户快照有效性与重放历史；凭据轮换后旧密文不得重建会话。
- 区分“以 UDP 承载 Mieru 会话”与“代理应用 UDP”，验收清单必须明确实际覆盖的组合。

验收：官方客户端 UDP 承载下的建连、双向大流量、空闲复用、目标失败、重传和撤权通过；注入重复包后应用字节和使用量都不重复；同端口重载及回滚继续通过。

### S3：稳定性与新旧性能对照

S0 完成后先采集基线；S1/S2 每完成一个切片补相同口径结果，最终对候选提交执行完整验证。

稳定性工作：

- 恢复 packet 周期、事件落盘与 observer 的真实入口覆盖；machine 场景使用固定 Core 的现有原生入口，不通过修改 Core 应用源码绕过契约。
- 增加至少 30 分钟持续负载场景，逐档提升至 1000 个会话，覆盖 TCP、UDP、mux 和混合流量。记录实际完成的负载；runner 容量不足时标记未完成，不当作通过。
- 在负载中循环新增/轮换/撤销用户、刷新授权、证书及同端口 Reload，并覆盖替换失败后的回滚和多 Node 隔离。
- 注入上游断开、客户端短写、限速取消、报告阻塞、慢盘、进程被杀及重启。坚持到期停止准入、旧代不复活、尾部不丢失和原周期重放。
- 收集 goroutine、FD、连接数、heap/RSS、吞吐、延迟、错误率和持久化队列深度。预热后进行重复负载与回收，按 GC 后存活对象及固定会话预算判断泄漏。

性能工作：

- 在 GitHub Actions 同一个受控 runner/job 中，构建并交替运行旧 `a1ad269` 与候选版本；固定 Go/toolchain、协议、证书、buffer、并发和目标服务，记录两份源码 SHA 与构建参数。
- 分别测试普通转发、`usage_v2`、本地事件模式；只比较双方语义等价的配置，不能把无计量转发与逐 I/O 计量混比。
- 同时测上传、下载、短连接和长连接，记录吞吐、p50/p95/p99 延迟、CPU/GiB、RSS、分配量与镜像/二进制体积。
- 预热后至少进行 5 组交替采样。吞吐和 CPU 以“不劣于旧基线 5%”作为初始调查阈值；越界需复现并说明原因。共享 runner 噪声大时结果为未决，不据此声称性能优劣。
- 在首次基线报告中记录并固定资源、延迟与误差阈值，再用于候选验收，不能在看到失败后放宽。

验收：新增原生会话稳定性 suite 在 Actions 执行；有提交绑定的持续负载及故障报告；A/B 报告明确可比范围和未决项。单机或回环结果只代表相应环境，不推广为跨地域实网证据。

### S4：补齐低优先级协议和运维能力

在 S0-S3 的结果基础上逐项推进：

1. Mieru `traffic_pattern`、padding/分片策略和低熵编码，使用官方客户端的显式配置验收。实现之前，非默认而尚不支持的参数应在配置校验阶段明确拒绝，避免配置接收成功但行为不生效。
2. 评估按连接 ID 关闭能力。先核对 Core/API 是否需要并已有稳定连接身份契约，再复用现有 Server 连接登记与关闭语义；跨重载、重复关闭和已退出连接需要明确行为。
3. 补充受限的诊断输出：活跃用户/会话、撤权关闭原因、鉴权代际、UDP 重组/重传、计量待完成状态及 Reload 结果。不输出凭据、密钥或原始业务内容，避免无界标签。
4. 发布配置变更说明，列出被移除的旧内核原生键，以及面板结构化 routes/outbounds 的支持边界。renderer 行为变化时更新对应指纹和版本。

这些能力按独立切片交付，不能用某个尚未实现的可选特性拖住已验证协议组合的受控试运行。

### R：发布修复和 Core 采用

与源码开发分别记账，发布阻塞不妨碍继续完成 S0-S4。

- 2026-10-21 经用户明确选择独立发布，当前目标为 `ghcr.io/anrcm0/txnode`，由 `ANRCM0/TXnode` 的 `GITHUB_TOKEN` 创建和发布。历史 Core 包的关联和权限问题保留证据，不再作为独立 Node 交付前提。
- 工作流 `packages: write` 和源码中的新路径不证明发布成功；以实际 registry push、不可变摘要和按摘要运行的 artifact 为准。历史包若另行恢复发布，再单独核对其 Manage Actions access 等包侧授权。
- 重试选定、不可变提交的发布，核对 amd64/arm64 manifest、源码标签、镜像摘要和 `dev` 提升。随后按摘要拉取并执行实际镜像冒烟，而非只验证本地构建镜像。
- 候选版本必须对发布提交跑完整互通、原生稳定性及真实 Core C2。正式打标签前评审 Node 版本号和变更说明，使用新标签；本方案本身不创建标签。
- Core 采用通过其单独的 Node pin 更新评审及跨组件验收完成，记录 Node SHA、Core SHA、renderer 指纹和镜像摘要。Node 合并不等于 Core 已采用。
- 准备受控试运行说明和回滚方法：优先记录旧/新镜像摘要及配置差异；验证新持久化状态是否允许旧版读取，未验证前不得直接用旧版接管同一状态目录。原始计量日志与账本证据必须保留。
